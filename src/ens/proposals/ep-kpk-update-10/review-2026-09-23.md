**Recommendation: NEEDS_REVIEW. Do not schedule the switch yet.** At Ethereum mainnet block **26,037,425** (2026-09-23
03:13:47 UTC, hash `0xfb29dae51cd328ec64208e4135cee8bbbb702d8e8d58aa6b3d58b11da297ce31`), the replacement Main Roles

## Policy and implementation assertions

The full event replay applied the historical Update #10 delta to old Main and compared it with new Main. Both have **151
active target permissions** and **332 configured functions**. The wider history census contains 161 target keys and 360
function keys, including 28 revoked function keys; the revoked slots were checked, rather than silently omitted. There
were **zero target/clearance/function mismatches**: 316 entries were byte-identical, 15 differed only by safe
Or-alternative order among children of identical operator/type shape, and one USDC transfer condition omitted a trailing
root Static Pass that imposes no constraint. Members, default role, and adapter differences are the intentional
old-Sub-to-new-Sub and MultiSend-version wiring. Neither Main had a Roles allowance nor another role. The replay fails
closed on unknown or reorged events, duplicate log positions, foreign-address logs, unsupported allowance histories,
unproven normalization cases, and any difference in new-Main members, modules, roles, default roles, unwrappers, avatar,
target or owner (exit 1; exit 3 while only the owner is wrong, as at this pin). The structural test pins the fixture's
contents by hash. A fresh fixture regeneration at the new block yielded the same five arrays as the committed
[`roleStateKeys.json`](roleStateKeys.json); only its snapshot block changed.

The new MANAGER policy has **1,437 condition nodes** across its 332 functions. None uses ArraySome, Bitmask, or the
three allowance operators, so those changed checker paths are not exercised by the reviewed MANAGER configuration. Fork
tests separately probe positive and negative vault, token-approval, Horizon, Pendle, syrup, distributor, old-module, and
Sub-forwarding cases. A positive Roles authorization probe may still fail at the downstream protocol for balance, proof,
or liquidity reasons; those probes prove the authorization boundary, not profitable or successful venue execution.

Batch negative controls show old Main with MultiSend 1.3.0 and new Main with both 1.4.1 entrypoints reject the same
batches with the same Roles error: a forbidden item anywhere, inner delegatecalls without the option, nested batches,
inner or outer value and non-canonical encodings. After the ownership transfer and the switch, no MANAGER path (pod or
Sub; call, DelegateCall or MultiSend) can call an `onlyOwner` function of the new Main, the Sub or the old Main, or
change the Endowment Safe's owners, threshold, modules or guard (`closureAfterTransfer.t.sol`). The only Safe
self-configuration MANAGER keeps, carried over from EP 6.23 and never used, is switching the fallback handler to the
pinned ExtensibleFallbackHandler (one way) and registering ComposableCoW as the CoW-domain verifier. MANAGER can also
send any amount of ETH, with empty calldata, only to the DAO Timelock (EP 6.39); both Mains are asserted.

Baseline provenance: the old Main's policy before Update #10 (137 targets, 301 functions) traces to 14 transactions,
kpk's test-Safe configuration before the May 2024 hand-off, which EP 5.12 adopted by reference (45 targets and 84
functions, none with DelegateCall), and eight executed proposals (EP 5.12, 5.14, 6.8, 6.23, 6.27, 6.38, 6.39, 6.41).

All three Roles deployments are exact 45-byte EIP-1167 clones: old Main points to upstream Roles **2.1.0** mastercopy
`0x9646fDAD06d3e24444381f44362a3B0eB343D337`; new Main and Sub point to **2.1.1** mastercopy
`0xF2964CE6161ce0e75964Fe7927cE114cb0B283D5`, as mapped by the
[upstream version registry](https://github.com/gnosisguild/zodiac-modifier-roles/blob/218a5164d739c107b132034436978e78cdd90c95/packages/evm/mastercopies.json).
On 2026-09-23, both saved Etherscan-verified source bundles and the Integrity and old/new Packer libraries were rebuilt
afresh with solc 0.8.21, optimizer 100 runs, Shanghai, and deployed library links. All five **executable** runtimes
matched fresh chain code after removing the 53-byte CBOR metadata; libraries additionally required normalization of
their leading PUSH20 self-address. Full metadata-inclusive bytecode did **not** match, so this is an executable-code

The verified source differences are the EIP-1271 `staticcall` success check, `_arraySome`

## Findings and required follow-up

1. **CRITICAL: external ownership of the replacement.** If enabled in the observed state, the test Safe's one-signer
   threshold can change new Main's policy without the Foundation timelock or Security Council veto. The fork regression
   shows that this owner can widen `sUSDS.transfer`, after which the pod can move the Endowment Safe's entire observed
   sUSDS balance. Transfer new Main ownership to the Endowment Safe **before scheduling**, then repeat the owner,
   module, policy, and executable-code checks at a pinned block. The successful-switch test deliberately simulates this
   transfer; its green result is not evidence that transfer occurred on mainnet. Only the test Safe can make the
   transfer (`onlyOwner`; the Endowment Safe, EndowmentTimelock and Foundation Safe revert), and it can also renounce
   ownership, freezing the policy. Because the executor is open, the switch executes nine days after scheduling whoever
   then owns the Main: the Foundation must confirm the transfer and a passing fail-closed gate (`failClosedGate.t.sol`)
   before it schedules, and the Security Council should repeat the gate before the operation becomes ready. kpk followed
   exactly this order for the current Modifier in May 2024.
2. **IMPORTANT: final execution wrapper has not been reviewed.** Publish or identify the actual Foundation `schedule`
   transaction, then compare the complete tuple and Safe wrapper byte-for-byte with the reference, including gas/failure
   behavior and current module predecessor. The lifetime timelock scan shows no schedule through this review pin. The
   Security Council's veto and nine-day delay pass in the **reference** fork simulation, not in an actual new operation.
3. **IMPORTANT: standing Sub delegation exceeds a fixed Harvest-only promise.** Pod owns Sub and can grant a third party
   any MANAGER-bounded subset or transfer Sub without a new ENS Safe transaction. New Main caps what Sub can execute,
   but the proposed three-distributor configuration is not a permanent cap. Pod is also a direct Main member. Confirm
   the intended delegation policy and controller of the proposed Harvest member before that configuration goes live.
4. **INFO: Harvest is still unconfigured.** There is no live Sub role/member configuration at the pin. Verify the actual
   role key, member addresses, permissions, recipient constraints, and adapters after deployment; the simulated
   configuration proves only its tested boundary.
